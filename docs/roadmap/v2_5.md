## Architecture direction

The project is moving from a repository organized mainly around runtime algorithms to a platform organized around three stable boundaries

```text
Offline Site Production
        ↓ READY Site Package
Runtime Navigation Capabilities
        ↓ project result semantics
Mission / BehaviorTree orchestration
```

Scene-specific differences belong in Site Packages

Algorithm-specific differences belong behind project adapters/policies

Business-task differences belong in Mission/BT

Changing a localization/planner/controller backend should not require rewriting business-level BT trees

## Existing foundations to reuse

### BT / Mission

- `agt_mission_manager` remains the single Mission Action/state/audit owner
- BehaviorTree.CPP remains an execution backend under Mission Manager
- existing project Action wrappers and bounded cancellation rules remain valid

### Offline assets

V25-09A already established useful foundations that V25-12 must extend rather than duplicate

- immutable Dataset / Bag provenance
- persisted Calibration Set binding
- Platform Profile binding
- Derivation Recipe
- site alignment
- map version manifest and stable content hash
- READY immutability
- Semantic Map / Coverage binding
- Route Asset revisions
- footprint / kinematic feasibility
- preview artifacts
- `src/agt_offline_assets`

V25-12A therefore introduces a Site Package root identity over these existing map/route contracts instead of creating an incompatible second map registry

### Runtime validation

V25-11 SOFTWARE_ONLY Gazebo closed the following chain

```text
canonical localization
→ map identity
→ static navigation map / Route
→ Nav2 planner/controller
→ project Safety command chain
→ Gazebo BUNKER physical motion
→ active fault injection
→ localization/sensor Safety response
→ observability timeline / metrics
→ machine-readable acceptance Gate
```

This validated runtime chain becomes the regression baseline for future real adapters and backend replacement

## V25-12A — Site Manifest & Asset Lineage

Goal: define one deployable Site Package identity without invalidating the existing map-manifest / route-asset lineage

The Site Package must bind

- `site_id`
- package/version identity
- site/map frame identity
- one or more map versions/epochs
- selected READY localization map
- localization prior metadata
- selected navigation map
- selected Semantic Map
- READY Route revisions
- Calibration Set
- Vehicle/Sensor Profile
- Benchmark/truth references
- stable hashes

First implementation should be CLI/schema/validation first

No GUI and no new runtime ROS interface are required for V25-12A

## V25-12B — Point Cloud Processing CLI

Extend the reproducible offline derivation chain with deterministic operations needed by the future Workbench

- crop / bounds
- voxel/downsample
- statistical/radius outlier filtering
- height filtering
- ground/terrain derivation
- replayable manual-edit patches where practical

Raw evidence remains immutable

## V25-12C — AGT Map Workbench MVP

Provide a visual frontend over the same offline contracts

MVP

- point-cloud selection / crop / delete
- processing recipe controls
- localization-prior region authoring
- semantic annotation
- offline route preview
- immutable revision export

The GUI is replaceable and must not become the asset truth owner

## V25-12D — Localization Prior Contract

Add a versioned region/voxel prior with coarse categories

```text
EXCLUDE / LOW / NORMAL / HIGH / LANDMARK
```

The prior is explicit metadata

Backend use of the prior must be declared through the localization/relocalization adapter

Changing PCD intensity alone is not treated as prior fusion

## V25-12E — Semantic + Offline Route Preview

Converge existing Semantic Map, Task/Coverage and Route Asset tooling on Site Package identity

Preview and feasibility shall use the same Vehicle Profile / footprint contract as runtime validation

## V25-12F — Benchmark Dataset & Offline Evaluator

Standardize

- benchmark metadata
- independent truth binding
- odometry / localization trajectory metrics
- relocalization response metrics
- degeneration evidence when exposed by the estimator
- CPU / RSS / processing / map-search latency

Measured quantities, estimator diagnostics and manual annotations must remain distinguishable

## V25-12G — Vehicle Package Export

Export only validated READY assets into a runtime package

Runtime loads an explicit package identity/hash and must not infer an asset from the newest file in a directory

This stage prepares the future `LoadSitePackage` project capability

## V25-13 — Real BUNKER + MID360 + FAST-LIVO2

Replace simulation authorities with real adapters while preserving as much of the V25-11 acceptance semantics as possible

Priority

1. real chassis command/odom closure
2. real MID360/IMU SensorHealth
3. FAST-LIVO2 canonical odometry
4. real Localization Authority input
5. Site Package loading
6. happy-path / fault / observability regression

## V25-14 — Long-duration Figure-eight Benchmark

Create a fixed real-site route and truth contract

Use repeated laps and time-based runs to compare estimator/fusion configurations

Monitor

- trajectory error
- relocalization events
- degradation intervals
- CPU/RSS
- map/search latency
- long-duration failures

## V25-15 — GNSS / RTK Global Navigation

GNSS is global correction/fusion evidence, not a replacement for continuous local odometry

Target ownership remains

```text
continuous estimator -> odom -> base
Localization Authority -> map -> odom
```

GNSS-denied and GNSS-recovery transitions require explicit validation

## V25-16 — Large-map / Long-term Runtime

Introduce when benchmark evidence shows the need

- tile/submap index
- candidate place retrieval
- nearby active submaps
- bounded cache / eviction
- memory acceptance
- map-search latency acceptance

Do not hard-code one fully resident global PCD as the permanent project interface

## BT capability evolution

Navigation should ultimately be consumed by Mission trees through semantic project capabilities such as

```text
LoadSitePackage
CheckTaskReadiness
EnsureLocalization
ExecuteRoute
NavigateToSemanticTarget
ExecuteCoverageTask
RecordBenchmark
ReturnToSafePoint
```

BT nodes must not encode backend package names such as FAST-LIVO2, NavFn or MPPI

Those implementation choices remain below the project capability boundary

## Research tracks

GNSS, wheel constraints and global fusion are promoted into the staged engineering roadmap where needed for V25-13+ validation

STD / Scan Context, advanced place recognition, seasonal/structural map research, learned traversability and advanced ESDF-based control remain research or optional tracks until a concrete acceptance target promotes them

## Scope rule

A future capability appearing in architecture or roadmap does not imply a runtime publisher, ROS interface or vehicle acceptance

Each implementation stage must keep existing ownership contracts, fail-closed Safety behavior and versioned asset identity intact
